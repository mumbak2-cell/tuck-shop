## 2. Work queue, in order

### 2.1 Egress fix — IN PROGRESS, highest priority

**Brief:** `.agents/briefs/egress-sync-fix.md`
**Branch:** `perf/offline-sync-egress`

A Sonnet session was handed this on 2026-09-07 and may already have a PR open. **Check
first** — do not start it twice.

Root cause: `src/lib/offline-sync.ts` re-downloads whole tables with `select("*")` every
5 minutes, on every signed-in page (`OrgProvider` is in the root layout,
`src/app/layout.tsx:56`), with no idle check — 288 full catalogue downloads per day per
open tab. That is essentially the entire 5.83 GB.

Three fixes: visibility gate, location scoping, narrowed selects. All client-side.

**Two things that must not be got wrong:**

1. The visibility gate must skip `refreshCache` but **not** `drainQueue`. Gate the wrong
   half and queued offline sales stop flushing while a till tab is backgrounded — silent
   data loss.
2. `OrgState.stockMode` can be `"central"` (shared stock pool across shops). Verify the POS
   online path before scoping stock by location. If central mode genuinely needs
   cross-location stock, **stop and report**.

**The PR is not acceptable without a byte measurement.** DevTools → Network → filter
`rest/v1`, total transferred over one 5-minute cycle, on `main` and on the branch, both
numbers in the PR body. Clean types and lint prove nothing here.

## 5. Guardrails — non-negotiable

- **Never `supabase db push`.** Every migration is applied by hand by Mumba in the SQL
  Editor, then recorded with `npx supabase migration repair --status applied <NNN>`. Remote
  migration history is sparse by design; `db push` would apply things never meant to go in.
- **Never apply migrations, GRANTs or policy changes while shops are trading.** PRs and
  reviews any time.
- **`main` auto-deploys production.** Two Vercel projects deploy from it (tilify-jimmy and
  tuck-shop). Open PRs; Mumba merges.
- **Never read PIN or credential values out of the database** to test a fix. Anything
  needing a real credential becomes an OWNER MUST VERIFY item for Mumba.
- **Migration files are not evidence of the database's state.** 035 proves it. Verify
  against `pg_policies` / `pg_proc`, not against the repo.
- **Later migrations silently undo earlier security fixes.** This has happened repeatedly —
  see migrations 113, 114, 115. Re-verify after applying anything.
