## The finding that matters

Revenue Assurance computed `unrecordedUnits = Math.max(unitsSold - recordedSales, 0)`.
That reports only one direction: units leaving the shelf without being rung up. The
reverse — more rung up than stock movement explains — clamped to zero and **displayed
as a green tick ✓**.

That reverse case is exactly what selling past available stock produces, and it is
reachable in normal trade: the POS deliberately warns rather than blocks
(`pos/cart.tsx`, "stock warning, not a block"), and `deduct_stock_at_location` floors
the result at zero, so the shortfall left no trace anywhere.

**On live data this was 307 units across 18 of 34 products**, every one previously
rendering as reconciled. The largest single row is 42 units.

Both directions are now reported (PR-less, commit `86b1c5d`), and migration 058
records each shortfall as it happens rather than inferring it from counts.

## Open threads

**1. Investigate the 307 units.** This is the real outstanding work. A 42-unit row is
far more likely an unrecorded delivery than 42 individual till overrides. Check those
products' recent `stock_receipts` before trusting their stock levels. These are
historic and inferred; from now on 058 gives exact timestamped events, so the two
should agree going forward and any divergence favours the recorded number.

**2. Twelve functions are executable by `anon`.** Migration 040 revoked `PUBLIC` from
twelve SECURITY DEFINER functions and reads as though it closed them. It did not —
Supabase's default privileges grant EXECUTE to `anon`, `authenticated` and
`service_role` **by name**, and `PUBLIC` is a different grantee. Verified: all three
functions checked still show `anon=X`.

**Not exploitable** — each calls `assert_org_writable()`, which resolves the caller via
`auth.uid()` and rejects anonymous before touching data. The guards are the real
protection. This is cleanup, not a fix, and is documented in CLAUDE.md so nobody
removes a guard believing the grant covers it. Doing it properly means
`REVOKE EXECUTE … FROM anon` on each, which wants its own testing.

**3. Receive Stock still orphans an abandoned upload.** Files upload on file-pick,
before save. The expense modal discards on cancel, but Receive Stock has no cancel
affordance and navigating away strands the object. `beforeunload` is unreliable and
would fire on legitimate navigation, so it was left alone deliberately. The upload
widget's X is the clean exit. `scripts/cleanup-orphaned-receipts.mjs` reconciles the
bucket (dry-run by default); it last ran clean — 1 object, 0 orphans.

**4. Storage headroom is not a concern.** One real receipt measured 0.20 MB, matching
the 50 KB–500 KB estimate. At that average the 1 GB free tier holds roughly 5,000
receipts — several years at ~20 expenses/week.

## Traps that cost real time this session

**The Supabase SQL Editor runs a script as ONE transaction.** 057 failed partway on an
`unnest()` error and *everything before it rolled back*, including ALTER TABLEs that
had appeared to succeed. Re-running "just the failing part" then left production with
storage policies but no columns and no bucket — while `migration repair` had already
recorded 057 as applied, so the history lied. **Migrations must be idempotent and
re-run whole from the top.** Both 057 and 058 now are.

**Verification queries must return ONE result set.** The editor only displays the last
statement's output, so a multi-query check silently hides the earlier ones. Use
`UNION ALL`. This wasted several exchanges.

**A missing column surfaces as "Unknown error".** PostgREST returns `PGRST204` as a
plain object, not an `Error`, so `err instanceof Error ? err.message : "Unknown error"`
hides the cause entirely. Read `.message` off the object.

**"Pushed but the site is unchanged" is usually a missing deploy.** Vercel silently
produced no build for one commit — no deployment record, no commit status, no check
run — while neighbouring commits deployed within a minute. An empty commit re-fires the
webhook. Check with the `gh api … /deployments` one-liner in CLAUDE.md before
suspecting cache or code.

**The Vercel CLI can exit 0 without doing anything.** `vercel project remove` ignored
`--non-interactive`, hit EOF on its confirmation prompt, defaulted to "N", deleted
nothing — and returned success. Never read exit 0 from it as proof. `--yes` does not
exist on that subcommand; pipe the answer and verify independently.
