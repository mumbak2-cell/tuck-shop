## What shipped this session (all merged to main and deployed)

The WMS CSV importer parsed rows with a naive `line.split(",")`, so any value
containing a quote kept its raw CSV escaping. Chichi's Bakes had 35 catalogue items
stored as e.g. `"10"" High cake box"` instead of `10" High cake box`. Those 35 rows
were repaired directly in the database, and `parseCsvLine()` was added to
`src/components/wms/csv-catalog-upload.tsx` so it cannot recur (#14).

The Paystack webhook was **completely inert in production** and nobody had noticed. It
logged events with `.upsert({ onConflict: "provider,provider_reference" })`, but that
index (migration 037) is **partial** (`WHERE provider_reference IS NOT NULL`), and
PostgREST's `onConflict` cannot target a partial index — every delivery raised
Postgres `42P10`, the error was swallowed by a destructured `const { data: logged }`,
and the handler returned `{duplicate:true}` while reconciling nothing. Fixed by using
a plain INSERT and treating unique-violation `23505` as the duplicate signal, plus
failing loudly on any other insert error. The same commit fixed `crypto.timingSafeEqual`
throwing a RangeError on a wrong-length signature (500 instead of a clean 401) (#15).

Pricing was refreshed to Starter R299 / R849 / R2,990, Growth R599 / R1,699 / R5,990,
Pro R999 / R2,799 / R9,990 (monthly / quarterly / annual). Quarterly now carries a real
~6% discount instead of being exactly 3× monthly; annual stays at two months free. The
dead MWK price block was deleted since billing is ZAR-only (#16/#17). The upgrade
button now shows the price and cycle it will charge — e.g. "Upgrade to Growth —
R1,699/quarter" — because the cycle toggle is separate from the button and it was easy
to buy the wrong cycle (#18/#19).

Auto-renewal was built (#20). Paystack recurring Plan codes are resolved server-side
per (tier, cycle) from environment variables — `PAYSTACK_PLAN_<TIER>_<CYCLE>`, nine of
them — in `src/lib/paystack-plans.ts`, deliberately not committed to source because
test and live codes differ per deployment and they must not reach the client bundle.
`initiate` passes `plan` when a code is configured and otherwise falls back to a
one-time charge, so the app was safe to ship before the Plans existed. The webhook
gained the recurring lifecycle: `subscription.create`, `invoice.payment_failed`,
`charge.failed`, `subscription.disable`, and `subscription.not_renew`.

Two follow-up fixes were needed once real Plans existed. Paystack's
`transaction/initialize` requires `amount` **even when a `plan` is supplied** — omitting
it returns "Invalid amount" — so `amount` is now always sent alongside `plan` (#21).
And subscription-lifecycle events carry **no org metadata** and can arrive *before* the
`charge.success` that stores the customer code, so `resolveOrgId` was losing them
(logged with `org_id` NULL, subscription code dropped). It now falls through
metadata → customer code → subscription code → **customer email** (`auth.users` →
`org_members`, deterministic under one-org-per-user), which has no ordering dependency
(#25). Five orphaned `org_id` NULL audit rows were backfilled; four remain NULL
because their orgs were deleted, which is correct.

## Hard-won Paystack facts worth keeping

A valid `plan_code` on `transaction/initialize` always creates a subscription, and the
plan's amount **overrides** whatever amount you send. Plan codes are per-mode: test
codes and live codes are different strings. Re-checking out the same plan with a
customer who is already subscribed does **not** create a second subscription and emits
no new `subscription.create`. Cancelling a subscription sends `subscription.not_renew`
(not `subscription.disable`); the webhook treats it as a no-op so the org keeps access
until `current_period_end`.

## How to work with Mumba

Concise and fact-based, no self-celebratory tone. Prose over bullet vomit. Minimal
solutions, no over-engineering. Verify before declaring done — this session's core
lesson was that three separate "fixes" were shipped on misdiagnoses before the actual
root cause was found by inspecting logged webhook payloads rather than reasoning from
symptoms. Take proactive action rather than only suggesting, except where the change is
high-risk: production data, financial flows, deletes. Hand over Supabase CLI and
production-database commands rather than running them; local `tsc`/`eslint`/git is fine.
